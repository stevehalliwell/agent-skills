# itch.io page kit

Prepare a local page kit, then when live setup is requested create the project as Draft and apply its theme. Saved forms are field references; confirm changes in the live editor.

## Workflow

1. Locate the project and output location. Inspect existing project notes, builds, images, and any prior page kit before asking for known facts. Default to `<project-root>/itch-page/` (or an existing release/publishing folder) and use [page-template.md](references/page-template.md) to create `page.md` there. Create `assets/` only when there are assets to put there. If project identity or root cannot be identified, ask one focused question. Done when the kit location and project identity are known and existing work is preserved.
2. Determine what is being listed **before** selecting form settings: ask what kind of build or project this is if existing files/notes do not establish it (for example Windows/macOS/Linux/Android downloadable game, HTML browser game, multiple build types, physical game, assets, or tool). Ask which platforms, whether players download files or play in browser, and whether builds exist yet; do not infer HTML from the saved form. Then record title, intended URL slug/account (if known), classification, corresponding itch kind, release status, pricing, and draft/restricted/public intent. Ask only material unknown choices one at a time and record answers immediately in `page.md`. Leave account/slug pending rather than inventing a public URL; check availability in the live form. Default visibility intent to Draft, never presume paid pricing or public release. Done when build type and corresponding listing choices are recorded or clearly pending.
3. Draft reader-facing content from evidence: distinct short tagline, page description (what the project offers, how to play/use it, key features, access needs), genre when applicable, up to 10 relevant tags without duplicating platform/genre, download/install instructions when needed, optional video/store links, custom noun, and community setting. Distinguish verified game facts from proposed copy; ask about claims that cannot be confirmed from game/materials. Keep rich-text sections as paste-ready prose in Markdown; itch's editor is not a Markdown importer, so check formatting after pasting. Done when each applicable field has copy or an explicit pending reason.
4. Plan build-specific delivery and media. Inventory files, platforms/architecture, packaging, runtime requirements, and optional channels. For downloads, record each platform's file, launch/install steps, and prerequisites; omit embed settings. For HTML, verify `index.html` at ZIP root (or self-contained `.html`) and record embed mode, viewport, mobile, autoplay, fullscreen, scrollbars, and SharedArrayBuffer needs. For physical games/assets/tools, record actual formats and usage instructions. Capture or request 3–5 real gameplay screenshots when applicable, or accurate product previews; never label mockups or AI art as gameplay. Request or create a cover only from authorized assets/tools; record origin, rights, dimensions, and approval. Saved form requires a cover (minimum 315×250, recommended 630×500; PNG/GIF/JPG/JPEG up to 3 MiB); recheck live limits. Put approved images in `assets/` or list missing shots/cover brief. Done when media is checked or gaps are explicit.
5. Resolve policy and release details: ask whether the project contains generative-AI output (including edited output), record the user's answer and disclosure selection; do not guess. Check pricing against account payment setup, links, platform tags, build readiness, and any itch quality-guideline issues. Mark unresolved fields `Pending`, not fabricated. Done when `page.md` has a field-by-field status and a concise remaining-actions checklist.
6. Record a theme plan in the same `page.md`: BG/BG 2/text/link colors, optional header/button colors and BG 2 alpha; body/header font and size; screenshot placement; banner image/alignment and background image. Ask for visual direction or propose a palette from approved art; check contrast and image legibility. Keep cover separate from banner/background; record theme asset paths, rights, and crop notes. Mark unknowns `Pending` or `Use default`, never borrow values from the example page. Done when theme settings and media are recorded.
7. If the user requests live setup, load `agent-browser` and enter the basic listing in the live new-project form. Review all values against `page.md`, choose **Draft**, and get approval for creating/saving the draft before clicking Save & view page. Record the resulting page URL and actual draft state in `page.md`; if creation fails, stop and record the blocker. For kit-only requests, stop before this step. Done when the draft exists and is verified, or no live setup was requested.
8. On the verified draft, open Edit theme, compare available controls with `page.md`, apply the agreed colors, fonts, layout, and theme images, and preview desktop/mobile readability. Get approval before saving theme changes; verify the saved theme and that the page remains Draft, then update `page.md` with applied settings and remaining gaps. Never switch to Public as part of this workflow. Done when theme is saved on the draft or the blocker is recorded.
9. Report the kit path, draft URL and theme status if created, and remaining blockers. Do not claim remote actions happened when only the kit was prepared. Done when local and remote states are clear.

## Boundaries

- A kit-only request stops at local files. A request to set up the itch page includes the Draft creation and theme steps, with separate confirmation before submitting each form. Draft is not Public; never enable Public or Restricted without explicit approval. Do not log in or upload builds without user direction and the required confirmation.
- Butler can push builds and manage upload channels **after a project page exists**; it cannot create or manage the project page. If requested later, note `butler push <build-folder> <account>/<slug>:<channel>` as a possible upload path, verify the actual build and destination, and do not run it as part of page-kit preparation.
- The saved new-project form and saved theme editor are examples, not defaults: their selected project type, status, colors, fonts, images, and layout must not silently become this project's choices. They may contain account/session data; never copy tokens or personal account details into the kit.
- For screenshots or cover generation, use available project image tools or request files from the user; do not claim to have generated or captured images when tools are unavailable. Verify rights to use third-party media.

## Reference

[Page template](references/page-template.md) maps fields observed in the saved new-project form and saved theme editor to a human-editable kit. It is not a form submission payload.
