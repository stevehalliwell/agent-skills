# Decision collection usage

This collection records durable system choices and their rationale, consequences, guardrails, and revisit conditions. Use it for consequential architecture, frameworks, public APIs, data models, schemas, migrations, security, operations, dependencies, or cost decisions. Keep routine reversible implementation choices and task progress in task records instead.

## Check existing decisions first

Before framing a new choice, find related decisions by topic and `revisit_triggers`. Read those records for agreed choices, rejected alternatives, accepted costs, guardrails, and conditions for reopening the discussion.

An accepted decision remains a constraint until the user agrees to change it. A revisit trigger warrants review, not automatic reversal. Make conflicts with existing decisions explicit before dependent work proceeds.

## Status and approval

- `proposed`: an option or recommendation awaiting user agreement. It is not implementation authorization or an accepted constraint.
- `accepted`: the user has agreed to the choice and its guardrails. Do not mark an agent recommendation accepted without that agreement.
- `superseded`: a previously recorded choice has been replaced by a user-agreed decision. Link the replacement and explain why the old choice no longer governs; retain the old record for history.

A direct user decision can be recorded as `accepted` without first creating a proposed record. Discussion alone does not require a record for every option. When an existing accepted choice is replaced, save and verify the replacement before marking the old record `superseded`. Do not rewrite the old rationale as though the replacement had always been chosen.

If the user defers or cancels a discussion, leave any existing proposal unaccepted and explain the unresolved state in its body. Do not invent a status outside the schema. Do not resume work that depends on an unresolved choice.

## Record contents

Use `.template.md` as starting structure, not mandatory headings. Lead with the choice and its point; show representative code, interfaces, schemas, or artifacts for technical choices where useful. Record only relevant context, rejected alternatives and rationale, accepted costs/risks, affected areas, guardrails, and revisit conditions. Give each fact one home; link related records rather than duplicating them. Omit irrelevant headings and empty placeholders; keep unresolved material choices explicit. Use one final Comments section for errata and incidental notes, omitted until populated; update agreed corrections in the relevant decision section. Keep documentation concise, ordered, structured, and free of secrets or chat dumps.

`revisit_triggers` is an array of stable kebab-case tags representing conditions that should reopen discussion. Explain each tag's concrete condition under `Revisit trigger` in the body. Derive tags from the actual decision context rather than inventing speculative conditions. An empty array is valid when no trigger has been identified; make that absence explicit in the body.

## Recording and resuming work

`tradeoff-review` owns comparing options, obtaining the user's decision, and recording the result. Verify that the saved choice, consequences, guardrails, and revisit conditions accurately reflect the agreement; correct discrepancies before dependent work resumes.

Record existence does not authorize implementation. Return to the calling workflow after the agreed decision is saved and verified; implement only when the user's request authorizes that work. Handoffs and task records link to the decision rather than duplicating its rationale.
