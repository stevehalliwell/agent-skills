# Task collection usage

This collection is the canonical backlog and work tracker. It defines task readiness, selection, progress, and completion approval.

## Creating and shaping work

Create one record for each independently reviewable outcome. Capture supplied facts and constraints without inventing scope, acceptance, or product decisions. New unshaped work starts in `needs-refinement`. Use a supplied numeric priority when available; otherwise use the schema default, `0`, for normal priority. Preserve existing state and priority when adding detail unless a change is requested.

Keep unshaped work out of implementation. Refinement establishes shared understanding of what the completed task is and is not, not merely an implementation plan. Before moving it to `todo`:

- Lead with the completed result and its point. For technical work, specify the important interfaces, code/data flow, and constraints—not just eventual user value.
- Show concrete examples in the task's medium: API/library work needs declarations and caller code; refactors need before/after code or artifacts; CLI/build work needs commands, outputs/artifacts, and exit status; data/storage work needs schemas or records and resulting data; UI/game work needs inputs/interactions and resulting visible state. Bug/performance work needs reproduction/workload and expected behavior or measurement method. Nontechnical work does not need code.
- Add ownership/lifetime, limits, error behavior, preserved behavior, and non-goals only where relevant. Label unsettled examples Proposed or Open; do not invent interfaces or guarantees to fill a heading.
- Tie observable acceptance and expected verification results to the contract and examples by reference, not by repeating them.
- Present that picture to the user and resolve material product decisions through user input. Settled requirements and answers do not need a separate final approval gate.
- Check whether materially different results could still satisfy the wording or examples rely on unagreed behavior. Correct gaps and recheck; keep the task unready if blocked. No identified questions alone does not establish readiness.

Persist confirmed details and answers as refinement proceeds. Keep unresolved product behavior and proposals awaiting agreement under `Open questions`; `TBD` does not authorize choosing behavior.

For a requested backlog-refinement pass, select `needs-refinement` records oldest first by `created_at`, then record name as a tie-breaker. Refine one item at a time using `task-refinement`, save it ready, then continue to the next eligible item. Pause on a material decision, blocker, or explicit user pause; do not implement or reprioritize during refinement.

## Status meanings

- `needs-refinement`: captured work needing clearer outcome, boundaries, or acceptance before selection for implementation.
- `todo`: refined, prioritized, and ready to select.
- `doing`: active implementation, including intermediate slices.
- `review`: the entire task is implementation-complete and awaits final user review or approval.
- `done`: approved by the user and complete.
- `deferred`: intentionally paused; record the reason and reconsideration trigger.
- `blocked`: waiting on a dependency or answer; record the blocker and what would unblock it.
- `defunct`: no longer relevant; record why.
- `willnotdo`: deliberately not to be implemented; record the rationale.
- `combined`: folded into another task; link the replacement record and preserve relevant confirmed detail there.
- `split`: replaced by smaller independently reviewable tasks; link those records and account for the original scope.

## Selection, priority, and dependencies

Keep only one task `doing` at a time. Before switching, update or block the current item. Start ready `todo` work by setting it to `doing`; resume authorized `doing` work without resetting its state. Do not start unready or blocked work.

For implementation selection, sort numeric priority highest first, then oldest `created_at`, then record name. `0` means normal priority, positive values raise priority, and negative values deprioritize work without pausing it. Values express relative ordering, not fixed urgency categories. Use `deferred` for intentional pauses. Do not reprioritize without a request. Backlog refinement uses creation order rather than priority order.

Use `depends_on` for task records that block progress, with references in `tasks/<name>` form. A dependency or unresolved acceptance question can make a nominally `todo` task unsafe to implement; report it rather than trusting status alone.

## Implementation and approval

Before starting or resuming implementation, read the agreed task context: whole-task goal, technical shape, non-goals, acceptance, and remaining slices. Keep that contract in the task record. Proceed when details are settled; resolve material gaps rather than silently choosing behavior. Do not add a routine pre-tool summary or a new approval gate.

Record material decisions, behavior changes, and meaningful checks during implementation. Keep `doing` while work has remaining slices. Update the checkboxes under `Plan` as slices finish; the next unchecked slice identifies remaining work. Keep actual validation evidence under `Checks`, separate from the expected results under `Acceptance`. The final plan item prepares the whole task for review; it is not implementation scope or completion approval. Do not toggle `review` between slices.

Set `review` only when the entire task is implementation-complete and awaits final user approval. Set `done` only after the user approves completion. Ending an iteration mode or requesting a summary alone is not completion approval. Retain completed records for search and history; do not archive or duplicate them into another tracker.

## Record contents and handoff

The title and name identify one independently reviewable task. Use `.template.md` as starting structure, not a mandatory checklist. During refinement, read it and add missing material contracts/examples without replacing confirmed details. Use concise, ordered, structured documentation: result and point first, important technical shape and examples next, then relevant boundaries, acceptance, open questions, plan, and checks. Omit irrelevant headings and empty placeholders; retain material unknowns explicitly.

Give each requirement one home. Put agreed interfaces, design choices, and constraints in the technical specification; acceptance references them, Plan tracks delivery slices, and Checks records actual evidence and unrun checks/risks. Do not repeat the scope as refinement summaries or append an answer log.

Use one final `Comments` section for errata and incidental notes; omit it until there is content. Do not add a separate Notes section. When a comment changes agreed behavior, update the relevant specification section and remove or clearly mark superseded instructions. Exclude chat dumps, secrets, and routine intermediate tweaks.

Handoffs point to records or exact queries. Each actionable next step has a work record; `.pi/handoff.md` is a pickup pointer, not a task tracker.

## Workflow ownership

- `backlog-capture` captures, deduplicates, and creates one or several task records.
- `pick-up` queries candidates and selects work to resume.
- `refine-the-backlog` selects unready items and iterates through single-task refinement.
- `task-refinement` agrees implementation shape and records the ready state when requested.
- `implementation` delivers agreed work and records checks and progress.
- `iteration` records one completed bundle rather than every tweak.
- `wrap-up` updates work state before writing a handoff.
- `tradeoff-review` records durable choices in the decisions collection, not task mechanics.
